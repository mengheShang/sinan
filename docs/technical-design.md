# Sinan Technical Design v2.1

Nov 4, 2026 · @Menghe

## 概述

Sinan 第一阶段交付一个可公开演示的 AI 邮件行动系统：提取 DDL 和待办，整理收件箱，并在用户批准或授权后执行操作。每一步都可追溯。

本版取代 v1.0 的第一阶段方案。主要变化有三点：

- 起点从本地文件管理改为邮件和 DDL，因为它使用频率更高，也更容易衡量效果。
- 架构从云端加本地 Agent 改为单机 Docker Compose，先降低部署和安全负担。
- 成功标准从功能数量改为可复现的评估结果和安全保证。

设计原则：

- **模型只提建议**：LLM 没有任何工具权限，只能输出结构化结果。
- **事实可追溯**：每条待办都能回到原始邮件和具体证据。
- **写操作需授权**：每个外部写操作都要有单次批准或有效的长期授权。
- **重复执行安全**：同步和写入可以重试，不产生重复结果。
- **公开优先**：仓库和演示只使用合成数据。

## 范围

第一阶段做一条完整链路：邮件进入，生成待办或动作，经批准或授权后执行。

| 类别 | 内容 |
| --- | --- |
| 纳入 | 两个 Google 邮箱的同步（USC 和主力邮箱） |
| 纳入 | DDL、待办提取，证据校验，DDL 变更识别 |
| 纳入 | Dashboard：摘要、待办、来源、审批 |
| 纳入 | 日历写入、标记已读、标签、归档、退订和审计日志 |
| 纳入 | 评估集、提示注入测试、CI、假数据演示模式 |
| 推迟 | Local File Agent、跨设备同步、Windows 支持 |
| 推迟 | 163、北大校友邮箱、Apple Calendar、课程平台 |
| 推迟 | 回复草稿、Planner、领域包、混合云部署 |
| 不做 | 自动发信、自动删信、银行连接、自动提交网申 |

### 验收标准

1. 新邮件能在一个同步周期内进入系统，重复同步不产生重复记录。
2. 每条待办都显示原邮件链接和证据原文。
3. 在隔离测试集上公布精确率和召回率，结果可复现。
4. 所有提示注入用例都不能绕过批准或授权，也不能产生未授权的写操作。
5. 同一操作重复执行时，只生效一次。
6. 每个外部操作都能追溯到邮件、批准或授权，以及执行结果。
7. 自动已读和标签只在有效授权内发生，可以撤销，并出现在每日摘要中。
8. 退订只在用户批准后执行，且只使用通过校验的一键退订请求。
9. 新用户无需 Google 账号或 API Key，用一条命令即可运行演示。

### 最终形态

长期系统由五个核心模块和四个领域包组成。第一阶段实现连接、理解、数据溯源和行动安全四层的最小版本，规划层留到后续。

| 层 | 职责 | 第一阶段 |
| --- | --- | --- |
| 连接层 | 接入邮箱、日历、课程平台和文件 | Gmail、Google Calendar |
| 理解层 | 提取事实并处理冲突 | DDL 和待办 |
| 数据与溯源层 | 保存信息、来源和历史 | 消息、待办、版本 |
| 规划层 | 排日程并解释原因 | 暂不实现 |
| 行动与安全层 | 权限、审批、执行和审计 | 日历和邮箱动作 |

学业、求职、健身和财务作为领域包，复用以上五层。

## 系统架构

第一阶段是运行在一台电脑上的模块化单体，由 Web、API、Worker、Executor 和 PostgreSQL 五个容器组成。

&#91;embedded content: 第一阶段系统架构 · 单机部署\]

Worker 使用只读令牌，没有任何写权限。Executor 持有写令牌，只执行已批准或已授权的动作，这是唯一能写外部服务的模块。

### 技术栈

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 前端 | Next.js、TypeScript | 全栈求职常见，页面需求简单 |
| 后端 | Python、FastAPI、Pydantic | 适合 LLM 工作，类型校验方便 |
| 数据库 | PostgreSQL、SQLAlchemy、Alembic | 约束和迁移可靠 |
| 定时任务 | APScheduler | 单机足够，不引入消息队列 |
| 部署 | Docker Compose | 一条命令启动 |
| 测试 | pytest、Playwright | 覆盖后端和完整流程 |
| CI | GitHub Actions、gitleaks | 自动测试和扫描密钥 |

暂不使用 LangGraph、向量数据库和消息队列，等主链路遇到明确需求时再评估。

### 目录结构

```text
sinan/
├── apps/
│   ├── api/          # FastAPI 路由
│   ├── worker/       # 定时同步和提取
│   └── web/          # Next.js Dashboard
├── app/
│   ├── providers/    # Gmail、Calendar、LLM 及假实现
│   ├── extraction/   # 预筛、Prompt、校验
│   ├── items/        # 事项匹配和版本
│   ├── actions/      # 授权、审批和执行
│   ├── audit/        # 审计日志
│   └── db/           # 模型和会话
├── evals/            # 评估脚本和合成数据
├── migrations/
├── tests/
├── docs/adr/         # 架构决策记录
└── docker-compose.yml
```

外部服务都放在 `providers` 接口后面。这样后续接入 163 邮箱时，不需要改动提取和审批逻辑。

## 数据模型

第一阶段用 11 张表，全部使用 UUID 主键和 UTC 时间。v1.0 的通用 `personal_facts`、`permissions` 和文件相关表暂不创建。

| 表 | 用途 | 关键约束 |
| --- | --- | --- |
| `accounts` | 已连接的账号及其角色 | `(provider, email)` 唯一 |
| `credentials` | 加密后的 OAuth 令牌 | 按账号和用途（读、写）各一行，绝不进日志 |
| `sync_states` | 每个账号的同步游标和错误 | 每个账号一行 |
| `messages` | 邮件元数据和正文 | `(account_id, provider_msg_id)` 唯一 |
| `extraction_runs` | 模型、Prompt 版本、耗时和结果 | 同一邮件和版本只处理一次 |
| `items` | 待办和 DDL 的当前状态 | 保存课程、标题、到期时间和状态 |
| `item_versions` | 每次变更的前后值和来源 | 只追加，不修改 |
| `proposals` | 等待决策的动作提案 | 保存动作类型、载荷及其哈希 |
| `grants` | 用户设置的长期授权 | 保存动作、范围、上限、到期和撤销时间 |
| `actions` | 所有外部操作的执行记录 | `idempotency_key` 唯一，来源必须是提案或授权 |
| `audit_events` | 所有关键动作的日志 | 只追加，不修改 |

### 关键字段

- `items.status`：`open`、`done`、`dismissed` 或 `needs_review`。
- `proposals.status`：`pending`、`approved`、`rejected`、`expired` 或 `executed`。
- `proposals.payload_hash`：对操作内容做 SHA-256。执行前重新计算，不一致就拒绝。
- `grants.scope`：账号、发件人白名单和动作类型的组合，不接受模糊描述。
- `actions.idempotency_key`：由来源和目标确定性生成，用于防止重复执行。
- `actions.undo_payload`：撤销操作需要的信息。退订没有这个字段。
- `item_versions.evidence`：支持这次变更的原文片段，以及它所属的邮件。

### 时间字段

到期时间同时保存原文和解析结果。例如原文“Friday 11:59pm”保存在 `due_raw`，解析后的时间保存在 `due_at`。缺少日期、时区或年份不明确时，设为 `needs_review`，不让模型猜测。

## 核心流程

主链路分为三段：理解邮件、等待批准、安全执行。任何一段失败，都不会产生未授权的外部写入。

&#91;embedded content: 从邮件到动作的主流程 · 12 步\]

### 邮件同步

1. 首次同步只拉取最近 30 天的邮件。
2. 之后用 Gmail 的 `historyId` 增量同步，并在事务提交后才更新游标。
3. 游标过期时，退回到最近 7 天重新同步。
4. `messages` 的唯一约束负责去重，所以重复拉取不会产生重复记录。

### 预筛和提取

预筛用发件人、域名和关键词排除明显无关的邮件，以减少费用和隐私暴露。通过的邮件进入 LLM，模型只返回下面这种 JSON：

```json
{
  "items": [{
    "kind": "deadline",
    "course": "CS 000",
    "title": "Homework 3",
    "due_raw": "Friday 11:59pm PT",
    "evidence": "Homework 3 is now due Friday at 11:59pm PT",
    "change_type": "update"
  }]
}
```

确定性代码随后完成校验：

- 用 Pydantic 校验 JSON 结构。
- 确认 `evidence` 确实出现在邮件原文中。
- 确认 `due_raw` 的主要内容能在证据中找到。
- 由代码结合邮件日期和时区解析 `due_at`，模型不直接给最终时间。

### DDL 变更

以“教授把 HW3 延期”为例：

1. 系统按课程和标准化标题查找已有事项。
2. 只有一个高置信度候选时，生成变更提案。
3. 有多个候选或没有候选时，标记为 `needs_review`。
4. 较旧的邮件不能覆盖较新邮件确认过的时间。
5. 用户批准后，追加新的 `item_versions` 记录，旧版本继续保留。

### 动作和授权

动作按风险分为三级：可撤销的动作可以用长期授权自动执行，难撤销或影响较大的动作要逐次批准，高风险动作不进入系统。

| 动作 | 策略 | 可撤销 | 执行方式 |
| --- | --- | --- | --- |
| 标记已读、加标签 | 长期授权后自动 | 是 | Gmail 修改标签 |
| 归档 | 长期授权后自动，或逐次批准 | 是 | 移除 `INBOX` 标签 |
| 新建日历事件 | 逐次批准 | 是 | 写入专用日历 |
| 修改日历事件 | 逐次批准 | 是 | 保存旧值后更新 |
| 退订 | 逐次批准 | 否 | 一键退订 POST |
| 发信、删信、改设置 | 系统不支持 | 否 | 不实现 |

授权由你在 Dashboard 中明确创建，模型不能创建或修改授权。一条授权示例：“USC 邮箱中，来自这 5 个发件人的邮件，如果没有提取出待办，可以标记已读，90 天后过期。”

自动动作还要通过以下检查：

- 发件人必须在授权白名单内，模型的分类结果不能单独触发动作。
- 邮件不能关联待办，也不能被判断为紧急或需要行动。
- 每次同步最多处理固定数量的邮件，超过上限就暂停授权并通知你。
- 每日摘要列出所有自动动作，并提供一键撤销。

### 退订

退订无法撤销，而且请求地址来自不可信的邮件头，所以规则最严格。系统只自动发起 RFC 8058 一键退订，其他情况只给你显示原始入口，由你自己判断。

1. 确认邮件同时包含 `List-Unsubscribe` 和 `List-Unsubscribe-Post`。
2. 确认 DKIM 通过，签名覆盖这两个邮件头，且签名域与发件人一致。
3. 确认地址使用 HTTPS，并拒绝内网地址和带账号信息的 URL。
4. 展示发件人、域名和目标地址，等待你逐次批准。
5. 只发送一次不带 Cookie 的 POST，不跟随跳转，并记录响应。
6. 不打开邮件正文中的退订链接，也不处理 `mailto:` 退订，因为后者要求发信。

提交成功只表示对方收到请求。系统继续观察该发件人后续是否还有邮件，并在摘要中标记结果。

### 审批和执行

提案显示原值、新值、证据和原邮件链接。用户批准后，Executor 依次复核状态、有效期和 `payload_hash`，再执行动作。长期授权执行前，Executor 还要复核授权是否仍有效。

所有动作都有确定性的幂等键。日历事件 ID 由提案 ID 生成，邮箱标签动作本身可以重复执行。退订在发送前先写入 `actions` 记录，所以进程崩溃后不会自动重发，而是标记为待人工确认。执行后再读回验证，结果和审计链路一起保存。

### 每日摘要

Worker 每天早上生成一次摘要，包括新增事项、DDL 变更、未来 7 天的到期事项、待审批提案和所有自动动作。第一阶段只在 Dashboard 中显示，不向外发送。

## 安全与隐私

最大的威胁是恶意邮件诱导系统执行操作，所以邮件内容始终被当作数据，模型也拿不到执行权限。

| 威胁 | 防护措施 | 验证方式 |
| --- | --- | --- |
| 邮件中的提示注入 | LLM 无工具；输出经 Schema 校验 | 注入测试集 |
| 诱导系统自动已读或归档 | 发件人白名单、固定上限、每日列出并可撤销 | 注入测试和集成测试 |
| 伪造或恶意的退订请求 | RFC 8058 和 DKIM 校验、URL 校验、逐次批准 | 恶意邮件头测试集 |
| 访问内网或本机服务（SSRF） | 解析后拒绝内网 IP，不跟随跳转 | 集成测试 |
| 伪造或夸大的 DDL | 校验证据原文；变更需人工审批 | 单元和评估测试 |
| 审批后载荷被篡改 | 执行前校验 `payload_hash` | 集成测试 |
| 重放或重复执行 | 提案一次性使用，并设置过期时间 | 集成测试 |
| 写令牌被滥用 | 只有 Executor 可解密，动作白名单，禁用发信接口 | 静态检查和代码审查 |
| 令牌泄露 | 加密存储，日志脱敏，读写令牌分离 | 代码审查和密钥扫描 |
| 隐私数据进入仓库 | 真实数据只留在 Git 外，CI 扫描 | gitleaks |
| 本地服务被访问 | 服务只绑定 `127.0.0.1`，Dashboard 需要登录 | 集成测试 |

### OAuth 权限

标记已读和归档需要 `gmail.modify`。Google 把这个权限描述为可读、撰写和发送邮件，所以不能再说“系统没有发信能力”。设计改为读写分离，把风险缩小并如实说明：

| 令牌 | 权限 | 持有者 | 允许的操作 |
| --- | --- | --- | --- |
| 读令牌 | `gmail.readonly` | Worker | 读取邮件和邮件头 |
| 写令牌 | `gmail.modify` | Executor | 只修改 `UNREAD`、`INBOX` 和 Sinan 标签 |
| 日历令牌 | `calendar.events` | Executor | 只写专用的 Sinan 日历 |

写令牌只有 Executor 能解密。邮箱适配器不提供发送、删除或移到垃圾箱的方法，CI 也会拦截对这些接口的调用。这些是代码层的限制，不是 Google 层的硬隔离，所以写令牌仍然属于高敏感凭证。

如果 M0 发现只读方案已经够用，可以先不申请写令牌，把邮箱动作推迟。

### 发送给 LLM 的数据

- 只发送通过规则预筛的邮件。
- 发送前去除引用历史和不必要的头信息。
- 使用的 API 服务要先确认数据保留和训练政策。
- `extraction_runs` 不保存完整提示词，只保存版本和哈希。

### 公开仓库规则

- `.env`、令牌、数据库备份和真实评估数据都不进 Git。
- 评估报告只公开汇总指标，不包含真实邮件内容。
- 演示数据全部虚构，包括课程、人名和邮箱地址。
- PRD 中具体的个人账号信息不公开。

## 评估

评估是这个项目最重要的差异点：每次改动 Prompt 或模型后，都用同一份隔离测试集比较结果。

### 数据集

| 数据集 | 建议规模 | 位置 | 用途 |
| --- | --- | --- | --- |
| 真实开发集 | 约 100 封 | 本地，Git 外 | 调整 Prompt 和规则 |
| 真实测试集 | 约 50 封 | 本地，Git 外 | 只用于报告最终指标 |
| 合成样例集 | 约 50 封 | 公开仓库 | CI 和演示 |
| 注入攻击集 | 至少 30 个 | 公开仓库 | 安全回归测试 |

标注内容包括：是否存在待办、课程、标题、到期时间、是否修改已有事项，以及这封邮件能否安全地自动已读。标注由你完成，这是不能交给开发 Agent 的工作。

### 指标

| 指标 | 含义 | 初始目标 |
| --- | --- | --- |
| 事项召回率 | 真实事项中被抓到的比例 | ≥ 90% |
| 事项精确率 | 提取结果中正确的比例 | ≥ 85% |
| 时间准确率 | 匹配事项中到期时间完全正确的比例 | ≥ 95% |
| 变更匹配准确率 | DDL 变更关联到正确事项的比例 | ≥ 90% |
| 重要邮件误处理数 | 需要行动的邮件被自动已读或归档的次数 | 0 |
| 退订校验错误数 | 不合规邮件头通过校验的次数 | 0 |
| 注入成功次数 | 绕过批准或授权、触发写操作的次数 | 0 |

这些目标只是起点，看到第一批真实结果后再调整。漏掉 DDL 比多一条提案更糟，所以召回率优先于精确率。

### 回归规则

- CI 使用录制好的模型响应，不需要 API Key，也不产生费用。
- 改 Prompt 或换模型时，手动运行真实模型评估，并保存结果。
- 合成集上的任一核心指标下降超过 2 个百分点时，CI 失败。
- 注入成功次数大于 0 、重要邮件误处理数或退订校验错误数大于 0 时，CI 直接失败。
- 真实测试集使用次数要受控，避免把 Prompt 调到只适合这批邮件。

## 工程规范

Agent 负责实现，你负责决策和验收。任何代码合并前，你都要能解释它做了什么。

| 工作 | 负责人 |
| --- | --- |
| Schema、权限边界、架构决策 | 你决定，Agent 可提方案 |
| 评估标注和验收标准 | 你 |
| 功能实现和测试草稿 | Agent，你审查 |
| 真实账号、OAuth 配置和令牌 | 只由你操作 |

### 开发规则

1. 每个任务对应一个 Issue，写清目标和验收条件。
2. 每个 PR 只做一件事，并附测试。
3. Agent 只使用假数据和测试账号，不读取真实 `.env`。
4. 涉及 `app/actions/`、OAuth 或数据库迁移的改动，必须逐行审查。
5. Agent 犯的重要错误记入开发日志，作为面试素材。
6. 关键取舍写入 `docs/adr/`。

### 代码风格

- 使用简短语句，避免长链式调用，每一步赋给变量。
- 使用简洁的变量名。
- 函数保持短小，副作用集中在 `actions` 和 `providers`。
- 这些规则写入仓库根目录的 Agent 说明文件，比如 `CLAUDE.md`。

## 风险与开工前验证

最先要确认的是 USC 邮箱能否授权自建应用，这决定 M1 的接入方式。以下事项都要在 M0 完成验证，尚未逐项核实。

| 验证项 | 为什么重要 | 不可行时的备选 |
| --- | --- | --- |
| USC Workspace 是否允许授权自建 OAuth 应用 | 管理员策略可能直接拦截 | 用自动转发到个人 Gmail，并先确认合规 |
| USC 是否允许 `gmail.modify` | 写权限可能比读权限更受限 | USC 邮箱只读，邮箱动作只用于个人 Gmail |
| 学校政策是否允许把邮件发给第三方 LLM | 课程邮件可能涉及他人信息 | 只处理通知类邮件，或使用本地模型 |
| Gmail OAuth 测试模式的令牌期限和限制 | 测试模式的刷新令牌通常 7 天过期 | 接受每周重新授权，并在 Dashboard 中提醒 |
| 单人自用项目的 Google 验证要求 | 受限权限可能涉及审核 | 保持测试模式，只有你自己使用 |
| Gmail `history.list` 和日历自定义 ID 的行为 | 同步和幂等设计依赖它们 | 改用时间窗口同步和外部映射表 |
| LLM API 的数据保留、训练政策和结构化输出能力 | 影响隐私和实现方式 | 更换服务商 |

### 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 时间线过紧，与期末撞车 | 课程和项目互相挤压 | 每周复盘；11 月底未到 M2 就把发布延后 |
| 只快不验 | 表面完成，实际不可靠 | 里程碑以完成标准为准，不以日期为准 |
| Agent 生成的代码超出理解范围 | 难以调试，面试讲不清 | 小 PR；讲不清就不合并 |
| 自动动作处理错邮件 | 漏看重要通知 | 从白名单和小上限起步，所有动作可撤销 |
| 写令牌风险 | 代码缺陷可能产生严重后果 | 读写分离，先在测试账号验证 |
| 邮件格式差异大 | 提取质量不稳定 | 先聚焦 USC 课程通知 |
| 评估数据太少 | 指标看起来好但不可靠 | 公布样本量，持续积累 |
| 项目范围再次膨胀 | 主链路迟迟不完成 | M4 之前不新增连接器和领域包 |

### 第一阶段之后

完成 M4 后，优先接入课程平台官方日历，然后做 Planner，最后恢复 Local File Agent。求职、健身和财务按实际需要逐个加入。
